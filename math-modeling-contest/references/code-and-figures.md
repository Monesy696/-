# 数学建模代码与论文图表专项规则

本文件用于已明确模型后的代码实现、计算验证、结果导出和论文图表生成。目标是让参赛队能看懂、能修改、能答辩，并能在另一台电脑上稳定复现论文中的关键数值、表格和图形。

## 一、代码规则

### 1. 先对齐模型，再写代码

- 实现前列出：输入数据、输出指标、核心变量、目标函数/推导式、约束、参数、验证方法和对应论文图表。信息不完时明确写出假设，不自行补造数据或结论。
- 在首次实现中优先保持公式到代码的直接对应。不为缩短行数使用难核对的嵌套表达式、链式调用或黑箱封装。
- 核心算法不得只给出伪代码或占位函数。使用库函数时，必须明确输入、参数、输出和它在模型中对应的数学步骤。

### 2. 适度分文件，保留唯一入口

- 默认使用 `main.py` 作为唯一运行入口；它只负责按论文逻辑组织“读取数据 → 预处理 → 建模/求解 → 验证 → 导出表格 → 生成图形”，不在主文件中堆放大段算法。
- 按真实责任拆分文件，常见为 `data_processing.py`、`model.py`、`validation.py`、`plot_results.py`。题目简单时可合并；只有当一个责任过长、被多处复用或有独立验证价值时才拆出新文件。
- 禁止为了形式分层创建 `utils.py`、`helpers.py`等杂物文件；通用常量很少时直接放在使用它的模块中。
- 每个函数完成一个可说清的建模步骤。参数过多通常表明责任边界不清，应先检查数据流，不默认引入类或复杂配置对象。

可按题目裁剪的目录形状：

```text
project/
├─ data/                 # 原始数据，不在运行中改写
├─ main.py               # 唯一入口
├─ data_processing.py    # 读取、清洗、特征/指标构造
├─ model.py              # 核心模型与求解
├─ validation.py         # 基线、误差、稳健性/敏感性
├─ plot_results.py       # 仅负责从结果生成论文图
├─ requirements.txt      # 经实测的最小依赖与版本
└─ outputs/
   ├─ tables/
   ├─ figures/
   └─ figure_data/
```

### 3. 正确性是硬门槛

- 核心算法至少完成四类检查中适用的部分：
  1. 手算或可穷举小样例，用于核对公式、索引和符号方向；
  2. 形状、类型、量纲、取值范围、单调性或守恒关系检查；
  3. 优化结果的约束可行性、边界条件和目标值回代；
  4. 与基线模型、独立公式、已知特例或另一种求解方法对照。
- 先核对中间量，再信任最终指标。数值异常、过于完美或反直觉时，主动排查数据泄漏、索引错位、单位错误、样本切分、目标函数方向、约束松弛和随机性。
- 不在未记录的情况下丢弃数据、填补结果、截断负值、替换无穷值或改写优化解。所有会改变结论的处理都必须在代码和论文中留有对应说明。
- 验证代码与核心计算分开，避免用同一段错误逻辑同时产生结果和“验证”。

### 4. 高效但不炫技

- 先保证结果正确和可核对。只优化实测的耗时热点或明显不合理的复杂度，不为追求“高级”改写已验证的直观逻辑。
- 批量数值计算优先使用 NumPy/Pandas 的向量化操作；但当显式循环更能对应递推、状态转移或约束时，保留清晰循环。不用难读的嵌套推导式代替核心步骤。
- 避免在循环中重复读文件、重复拟合不变模型、重复计算不变矩阵或逐行追加 DataFrame。对大数据优先预分配、批处理或复用不变量，并保持实现可解释。
- 除非确有时限压力且能保证确定性，不引入多进程、GPU、JIT、缓存框架或自定义并行调度。

### 5. 注释和命名让评审快速看懂

- 文件和函数名按建模任务命名，变量名使用可理解的英文语义；必要时在第一次出现处标注与论文符号的映射，例如 `# demand_t 对应式(8)中的 D_t，单位：t/d`。
- 注释只写三类信息：这一步的建模目的、不显然的公式/参数来源、容易误解的单位/索引/边界。不逐行翻译代码，不写“这里进行数据处理”等空话。
- 复杂函数可用不超过数行的简短说明，写清输入、输出和核心假设；普通函数用好名称和必要行内注释即可。不使用长 docstring、满屏分隔线或自动生成腔的模板注释。
- 代码风格一致、朴素、简洁，但不刻意制造错别字、冗余或“学生痕迹”。参赛队需要能够解释每个核心函数和参数。

### 6. 可复现性要求

- 所有路径相对于项目根目录，并由代码创建所需输出目录。不依赖 IDE 当前目录、人工复制文件或本机盘符。
- 提供经实际运行验证的最小依赖及版本、Python 版本和单一运行命令。不放入未使用的库。
- 同时固定 Python `random`、NumPy 及所用模型/求解器的随机种子。时间切分、交叉验证、重采样、初始解和超参数搜索顺序也必须固定。
- 不依赖无序集合/字典的遍历顺序；导出前显式指定排序键、列顺序、编码、小数精度和缺失值表示。文件名不包含时间戳、随机编号或运行机器名。
- 对优化器、线性代数库或并行计算，显式设置算法、收敛容差、最大迭代次数、初值和线程数（适用时固定为 1）。记录求解状态，不把未收敛结果当作最优解。
- “结果完全一致”以可核对的论文结果为准：在锁定环境中，导出表的行列、文本、固定精度后的数值和文件名必须一致。不同 CPU/系统下可能出现浮点末位或字体渲染差异时，必须声明数值容差与有效位数；不虚假承诺跨平台图片二进制文件完全相同。

### 7. 输出直接对接论文

- 结果在内存中只计算一次，再由同一结果对象生成控制台摘要、论文表格和图源数据。禁止为了凑正文数值手工修改 CSV 或在绘图脚本中重新抄录数组。
- 输出实行稳定命名：`table_01_*.csv`、`figure_01_*.png/pdf`、`figure_01_data.csv`。文件名、列名、单位、排序、类别编码、保留位数和论文图表编号形成一对一关系。
- 对每个关键结果保留“全精度计算值”和“论文展示值”的区别。计算中不使用已四舍五入的展示值；所有“提高 x%”由未舍入的原始结果计算。
- 程序结束时只输出：核心参数、主要指标、验证结果、求解状态和文件位置。不刷屏，不把唯一结果只留在控制台。

## 二、图表规则

### 1. 图表是论据，不是装饰

- 对每张图先写一句“它要回答的问题”和一句“读者应看到的主结论”。无法回答明确问题的图不生成或删除。
- 根据比较任务选择图形：时序趋势用折线，类别比较用点图/柱图，分布用直方/箱线/小提琴，关系用散点与必要拟合，误差与敏感性用能显示不确定性的图。不因美观默认使用饼图、雷达图、3D 图或双 Y 轴。
- 结论依赖绝对大小时，坐标范围不得制造夸张视觉差异；若为展示局部波动截断坐标轴，必须清晰标明。双 Y 轴只在量纲确实不同且关系无法分图表达时使用，并将轴颜色与数据系列对应。

### 2. 数据、口径和文本一致

- 绘图函数只接收明确的数据和输出路径，不在函数内重新拟合模型、改数据或暗中计算另一套指标。
- 图中数据必须能回指到 `outputs/figure_data/` 中的对应数据文件；表格、图和正文引用的关键值来自同一计算结果。
- 标题、坐标、图例、单位、时间范围、样本数、误差定义和类别顺序必须与正文一致。当论文图题已能说明图意时，图内不再放冗长主标题。
- 统计线、拟合线、置信带、显著性和误差棒都必须来自真实计算，并在图注中说明口径；不为了“论文感”添加。

### 3. 论文排版和视觉规范

- 先按最终插图宽度设计，再确定字号、线宽和标记；在论文中缩放到单栏或页宽后，正文级文字、坐标刻度、图例和子图编号仍应清晰可读。
- 一套作品共用同一图形主题：字体、主色、同类系列颜色、线宽、标记、网格、小数位和图例顺序一致。统一样式可用一个简短函数或 `matplotlib` 样式字典实现，不需要建立主题框架。
- 优先使用色盲友好、灰度下仍可区分的低饱和配色。信息区分不只依靠颜色，重要系列同时配合线型或标记。避免 `jet`、彩虹色带、高饱和荧光色、渐变背景、阴影和无意义饰边。
- 默认弱化上、右轴脊，网格线细且置于数据下方。图例不遮挡数据；类别过多时优先排序、水平布局、分面或拆图，不把文字压成无法阅读的角度。
- 表格默认使用三线表思路：只保留有助于比较的列，表头含单位，精度与测量/模型误差匹配，不用过多小数营造虚假精确。

### 4. 中文、数学符号和导出

- 明确配置可用的中文字体和负号显示，对字体缺失给出清晰错误或提示，不静默导出乱码。若要跨电脑保持字形，应随交付物提供赛事允许且授权合法的字体，或指定各系统均可获得的替代字体。
- 数学符号、上下标、希腊字母和单位按全文统一的写法。不将数学文本和普通中文随意混用不兼容的字体。
- 导出前调用紧凑布局或显式调整边距，再检查标签、图例、色条、注释和标记是否被裁切。保存发生在 `show()` 之前，批量绘图后关闭图对象。
- 关键图默认导出 600 dpi PNG 和 PDF 矢量图；如果图中的庞大散点或热图使矢量文件过大，允许将该图层栅格化，其余文字和线条保持矢量。

### 5. 图表校验

- 代码校验：生成的图形数量、输出路径、文件名、数据行数、系列数、类别顺序和坐标范围符合预期。
- 数据校验：从图源数据中抽查极值、均值、关键拐点、基准线和置信区间，与正文和结果表格核对。
- 视觉校验：打开最终 PNG/PDF，检查中文、负号、上下标、坐标单位、图例、色条、子图编号、裁切、线型区分和黑白打印可读性。
- 论证校验：图注说清对象、口径和必要统计信息；正文在图表出现前引用，并给出具体读图结论，不只写“由图可知”。

## 三、联合验收

每次正式交付必须完成以下检查：

1. 在一个新建、空的 `outputs/` 目录上运行唯一入口，无人工中间操作即生成所有论文关键表格、图源数据和图形。
2. 用同一输入连续运行两次，比较稳定文件名、行列顺序、文本值和规定精度后的数值；不一致时查明随机源、并行性、求解容差或无序遍历。
3. 使用实际交付的依赖文件在新环境运行一次。如无法在当前环境完成，明确列出未验证项和风险，不宣称“可完全复现”。
4. 对照论文逐项核对模型参数、符号、单位、公式、有效数字、图号、表号、文件名和关键结论。
5. 给核心函数做代码审查：没有全局变量隐式传递、未记录数据修改、重复实现公式、静默失败、未处理的未收敛状态或与论文不一致的索引/单位。
6. 删除调试垃圾、未使用导入、死代码、无关图表、临时文件和占位数据；不因清理而改写已验证的核心计算。
7. 最终说明只保留：运行方式、数据位置、输出位置、随机种子、环境版本、关键结果映射和已知局限。

## 四、交付禁区

- 不生成或提供规避 AI 检测、伪造人类痕迹、隐瞒工具使用或欺骗赛事评审的方法。代码风格的目标是真实、易懂、与队员的模型叙述一致。
- 不为显得专业而增加类层次、配置中心、日志框架、命令行框架、插件、自定义异常体系、冗长类型标注或大量微型函数。
- 不为好看而更改数据、坐标尺度、样本范围、类别顺序、显著性、误差范围或模型结论。
- 不把“代码可运行”等同于“模型正确”，不把“图形美观”等同于“论证成立”。
